## What to reuse

ds-decomp automates analysis and project setup, delinks code into relocatable ELF objects, records symbols and relocations, generates linker inputs and objdiff configuration, and checks rebuilt modules. It does not itself turn all DS machine code into portable C. Its `complete` delinks flag selects a compiled replacement instead of the original delinked object. That provides a useful incremental replacement model. See the [command descriptions](https://github.com/AetiasHax/ds-decomp/blob/3b2df91c530ad144cbda0031abb7ce0eec3b1d83/README.md#commands) and [delinks format](https://github.com/AetiasHax/ds-decomp/blob/3b2df91c530ad144cbda0031abb7ce0eec3b1d83/docs/delinks.md#files).

SM64DS provides a concrete candidate-and-verifier loop:

1. Select one function or evidenced class boundary. Keep module, address, extent and source ownership explicit. Its current protocol uses a continuous producer, source review, independent verification and integration; older writer/builder role notes are historical references. See [the v2 protocol](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/notes/agents/PIPELINE.md#roles-and-continuous-ownership).
2. Draft a candidate, compile it and inspect a localized diff. [`fdiff.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/fdiff.py#L1-L18) exposes instruction differences so another source revision has a measurable purpose. Preserve unsuccessful candidates and the reason they failed.
3. Separate iteration from acceptance. [`build_pin.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/build_pin.py#L151-L199) derives the actual build compiler and flags; its strict relocation check must be supplied. [`match.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/match.py#L381-L419) enables strict checks by default but falls back to a byte-only comparison if its relocation infrastructure cannot load. Our acceptance step must fail when required proof is unavailable.
4. Verify linked bytes and destinations. A wildcarded relocation can hide the wrong callee or global. [`linkcheck.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/linkcheck.py#L1-L24) applies relocations and distinguishes verified, wrong and unresolved results. Preserve destination module, addend and instruction mode; ds-decomp explicitly distinguishes [ARM, Thumb and interworking relocation kinds](https://github.com/AetiasHax/ds-decomp/blob/3b2df91c530ad144cbda0031abb7ce0eec3b1d83/docs/relocs.md#relocation-kinds).
5. Check emitted data and the actual production link. A matching function does not prove its vtable, RTTI or static data. [`romdata_check.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/romdata_check.py#L1-L38) explains how an exact rebuilt ROM can still use original gap data rather than the candidate's emitted data. Its verdicts are measurements with a regression ratchet, not a universal pass. [TU promotion checks](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/notes/tu-promotion-conventions.md#L42-L58) also require that the normal build consumes the intended source.

## What the automation demonstrates

[`swarm.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/swarm.py#L1842-L1935) implements template proposals, compilation, comparison and recording of candidates. This is automated search with a compiler oracle; it does not require an LLM for those templates. Its header's claim of relocation-free templates is narrower than the current implementation, which also tries `RELOC_RULES`. Do not inherit its acceptance shortcuts.

The [SM64DS README](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/README.md#progress) reports 100% matched functions and recommends tangOS Console for coordinating AI-assisted work. Those are the project's reported results; this investigation did not reproduce its build, attribute the matches to AI, or establish an unattended success rate. Its [public validation workflow](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/.github/workflows/pr-validate.yml#L1-L6) explicitly says a green submission job is not the private validator's verdict.

## Toolchain compatibility

- Current ds-decomp HEAD still declares [version 0.12.1](https://github.com/AetiasHax/ds-decomp/blob/3b2df91c530ad144cbda0031abb7ce0eec3b1d83/cli/Cargo.toml#L2-L8). This project uses the older v0.12.1 source revision `73934550322c80b634106ad7883bbe4671f24b99` plus `tools/patches/dsd-0.12.1-thumb-retry.patch`. Preserve that proven baseline. Record revision, patch and executable hash; a shared version number does not prove identical behavior.
- SM64DS actively requires **dsd 0.11.0** in [`dsd_pin.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/dsd_pin.py#L1-L58). Its build cannot be transplanted unchanged onto our patched 0.12.1 setup.
- SM64DS defaults to **mwccarm 2004/b56**, with per-file exceptions, and separately uses the **1.2/sp2p3 linker**. Its compiler flags and EU-ROM addresses are evidence about that game, not Ghost Trick. See [`rombuild.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/rombuild.py#L72-L95). Ghost Trick's original compiler/version/flags remain unproven. Do not install proprietary compilers without the user's approval.
- Its comparison/template code assumes ARM word-oriented disassembly; Ghost Trick needs mode-aware handling of Thumb functions and literal pools. See [`match.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/match.py#L266-L330) and [`swarm.py`](https://github.com/tangosdev/sm64ds-decomp/blob/fecaa573767fd1680701871bfd1246e43d79e649/tools/swarm.py#L26-L40). Reuse the feedback loop, not an unchecked comparator or game-specific class definitions.

## Apply it here

The next implementation step is a **local function work packet and verifier** for a small Chapter 1 dependency. Generate it from the existing symbol/relocation configuration and known-good linked ELF. Include module-qualified range, ARM/Thumb mode, target hash, relevant disassembly, literal pools, incoming/outgoing relocations and a place for evidence-backed interface notes. Keep ROM-derived output under ignored `extracted/`; keep reusable tooling and synthetic tests tracked.

Record candidate source identity, compiler identity, exact arguments, object symbol extent and each verification result. Until a suitable compiler is approved and available, a packet can be ready and analyzed while its matching result remains **not run**. An all-assembly round trip, a Ghidra draft and a portable implementation are separate milestones.

Choose functions from the traced Chapter 1 path and hardware replacement boundaries. Verify recovered behavior against the DS oracle, then exercise Vita file, timing, input, rendering and audio replacements on-device. Byte matching supports recovery; it cannot prove a DS hardware call works on Vita. Keep the existing assembly baseline intact and avoid importing SM64DS's network queue, private service, ROM-derived source or full-game matching targets.
